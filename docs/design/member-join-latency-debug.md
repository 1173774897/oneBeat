# 队员加入队伍等待优化（2026-10-14）

## 现象与定位范围

队长在系统弹窗确认连接后，队员仍长时间显示「已找到队伍，正在请求连接队长」，随后才进入大厅。没有这次真机的分阶段日志，因此尚不能把观察到的等待全部归因于某一步；代码检查发现两个可复现的软件阻塞点。

加入码路径依次经过BLE找房间、Wi-Fi P2P连接与群组核对、TCP认证和11次时钟采样、renderer准备、后台保活，最终进入大厅。旧状态文案在找到房间后不再更新，任何后续等待都会呈现为「正在请求连接」。

## 已修正

1. **成功路径不再等待可选BLE拒绝反馈。** `AppSession.memberJoinWithInvitation`原来在`finally`中等待反馈初始化，再等待通道关闭。反馈建立可能经历两次3秒GATT连接超时及重试间隔，服务查询、注册写和关闭写还可能继续等待。认证、时钟和播放准备已经完成时，这个尾部等待仍会阻止页面跳转。现在同步取消尝试，通道清理由后台完成；失败也保留原失败原因，不被反馈清理盖掉。
2. **结束的BLE尝试停止未提交的注册。** `BleMemberJoinFeedbackAttempt`贯穿连接、服务查询、注册、重试和轮询；成功、失败及session关闭时取消。正在初始化的本地GATT句柄同步释放，异步继续执行前再次检查取消，不再发新的注册请求。服务查询和注册写各有3秒截止；取消写最多250ms，然后释放句柄。取消消息仍匹配旧attemptId，不删除新尝试。已经交给native的注册包是否迟到属于系统传输边界，现有测试不证明其送达顺序；BLE反馈始终仅为辅助，不代替系统P2P结果或TCP认证。
3. **P2P成功状态增加轮询兜底。** 原实现只在启动时查询一次`getP2pLinkedInfo`，后续每350ms只读取peer状态；若成功事件迟到或漏发，系统已连接也不能推进。现在每轮先查linked状态，只把`CONNECTED`作为成功；协商期查询到`DISCONNECTED`不推断为拒绝。事件路径仍立即响应，群组名/IP核对和拒绝/25秒超时语义保留。
4. **页面和日志呈现实际阶段。** 扫码及加入码都依次显示连接队长、已建立局域连接并同步队伍、准备进入大厅。`[JoinDiag]`只输出阶段、耗时和成功状态来源，不记录邀请口令、认证token、加入码或成员姓名。

初始11次时钟采样保持不变，固定采样间隔合计200ms加网络RTT；TCP认证、renderer准备和后台保活仍是进入大厅的条件。它们是确保成员和第一拍可用的步骤，没有为缩短等待提前放行。

## 验证

- `member-join-critical-path.cjs`运行实际AppSession加入方法：反馈初始化或关闭挂起均不阻塞已完成的加入；网络/认证失败立即保留原错误并清理；晚通道仍关闭；认证/时钟、renderer和后台准备条件仍被等待；session退出取消在途反馈；加入码的阶段回调正确传递。
- `ble-join-feedback-lifecycle.cjs`运行实际BLE代码：连接、服务查询、注册、重试取消；晚操作不继续注册；3秒操作截止；250ms取消写截止；晚读取不再拒绝或重新轮询；正常拒绝反馈和旧attemptId精确清理。
- `p2p-join-readiness.cjs`运行实际P2P代码：漏事件时下一轮350ms查询推进；初始未连接/临时查询失败不误拒绝；同步连接事件、BLE/设备/连接拒绝、超时与迟到查询都清理计时器/监听；正确群组成功，错误群组与空IP仍拒绝。
- 既有`latency-calibration-routing.cjs`回归通过，改动范围的空白检查通过。DevEco ArkTS编译及signed HAP构建成功（6.244秒），包为`entry/build/default/outputs/default/entry-default-signed.hap`，未安装到设备。

## 真机复测时如何判断剩余等待

从请求开始到`p2p-ready`包含系统确认、P2P协商和群组准备；`p2p-ready`到`clock-ready`包含TCP连接、房间认证及首轮时钟采样；随后是`renderer-ready`、`background-ready`及`lobby-ready`。Wi-Fi底层另输出`p2p-connected source=event/poll`。

软件测试确认已去掉这些可选等待和漏事件阻塞，不代表真机耗时已经测得。若确认后仍慢，应根据上述阶段的`stageMs`定位剩余系统协商或准备耗时，再决定是否继续优化。

## 退出后再加入误报其他 P2P 占用（2026-10-14）

用户反馈队员退出队伍后再加入，提示「设备正在使用其他 P2P 连接」。已在实际源码模拟中复现：队员成功加入后，`lastMemberAttemptGroupName` 已清空，仅旧 `WifiP2pManager.ownsGroup` 保留本应用归属；旧 `removeOwnedGroup` 调用同步的 `removeGroup()` 后立即清除归属并返回，但 SDK 返回只代表提交移除请求，系统仍可能是 `CONNECTED`。新会话的 manager 没有该归属，因此误判为其他应用。退出中音频或 BLE 清理失败跳过 P2P、并发 reset 提前丢掉旧实例、加入页在初始化清理期间直接创建会话，也会放大这一问题。

已修正：

- 移除应用自己的组后等待明确 `DISCONNECTED` 才释放归属；每 150ms 查询，移除后的确认等待最多 3 秒，失败保留旧 owner 供重试。记录实际加入/创建的组名，移除前核对当前组；空信息或未知连接状态不能当作已释放，已换成不同组则仅放弃旧归属，不移除当前连接。
- 在不同 manager 间共享在途释放 Promise。加入预检查在 SDK 查询前后均检查屏障，避免同一轮退出/加入时用过期连接快照误报；并发退出只提交一次移除。
- `AppSession.reset/clear` 共用在途清理，失败保留退役实例用于下一次重试，清理完成前不创建新会话。每个 session 的成功 shutdown 永久幂等，失败才允许重试；各资源的清理通过 finally 保证执行，音频/BLE 失败也不能跳过 P2P。迟到的旧房间退出回调不能停止新会话的全局监听或覆盖新页面。
- 加入页初始化、扫码与加入码通过 `prepareMember` 等旧会话清理并复用同一个新成员会话；不等待整轮权限预申请/附近扫描。后台预热核对请求与会话归属，不覆盖已开始的加入进度。初始化清理失败由页面呈现，下次加入可重试。

`p2p-rejoin-lifecycle.cjs` 对修改前源码在首个 300ms 延迟断开用例失败，修改后通过 300/1500ms 延迟、同一轮退出/加入、并发退出、3 秒确认超时、SDK 失败后重试、空组身份、未知状态与其他应用连接保护。`member-join-session-reset.cjs` 运行实际页面和 Session 静态方法，验证两种加入入口等待清理、只创建一个新会话、无额外扫描等待及失败重试。`session-reset-lifecycle.cjs` 运行实际会话方法，验证 clear/reset/shutdown 并发共用清理、各清理步骤单项失败仍执行后续步骤、失败重试、成功退出幂等以及正常/迟到远端解散回调。原 `p2p-join-readiness.cjs`、`member-join-critical-path.cjs`、校准路由与试音弹窗回归保持通过。

最终 ArkTS 编译和 signed HAP 构建成功（5.011 秒），包为 `entry/build/default/outputs/default/entry-default-signed.hap`，未安装到设备。改动范围的代码与新增文档/测试空白检查通过。

上述是源码行为验证，尚未取得本次真机退出与重加入日志。真机应在同一队伍重复「加入 → 退出 → 立即再次加入」，再检查切换其他队伍；若仍失败，保留 `[JoinDiag] stage=p2p-release` 的 `state/elapsedMs` 与完整加入阶段日志。真正由投屏、互传或附近共享占用 P2P 时仍提示原错误，不以自动断开其他应用连接绕过。

## 首次加入、队长同意后误报其他 P2P 占用（2026-10-15）

用户反馈此次是队员第一次加入，队长同意后立即出现同一占用错误，并非退出后重加。没有本次分阶段真机日志；实际源码模拟已复现一条能产生完全相同文案的路径，因此本轮修正的是已证实的软件竞态，不能据此断言这次真机事件只有这一原因。

复现顺序：首次预检查为 `DISCONNECTED`，提交一次 `p2pConnect`，队长同意后系统报 `CONNECTED`；当前组名已匹配邀请，但 `goIpAddress` 仍为空。旧 `waitForCurrentGroup` 只等组名，立即返回；`connectCandidate` 抛「已连接 P2P，但系统未返回队长地址」时尚未登记 `ownsGroup`。候选重试直接进入 `prepareMemberDiscovery → assertReadyForOneBeat`，把仍为 `CONNECTED` 的本次连接误判为外部连接，覆盖真实原因。最终 abort 也因没有 owner 而无法释放已匹配的组。既有测试直接调用候选连接，且把空 IP 立即失败作为预期，没有覆盖这条完整首次加入路径。

已修正：

- 成员连接新增 `waitForMemberGroup`，同时等待准确组名与非空队长 IP，每 250ms 查询，硬截止为 4 秒；正常信息已就绪时立即完成。组名一经核实就登记本次连接归属，再等待地址，保证地址暂缺时退出或失败仍可清理自己的组。日志只记录 `stage=p2p-group state=waiting-address/ready/timeout` 和耗时，不记录组名、IP、口令或邀请凭据。
- 本次组已核实但地址最终仍缺失时，保留原就绪错误，交给调用方 abort 清理；不重新进入外部连接预检查。其他候选失败先收尾该次尝试，再重新发现，避免遗留的本次连接进入无归属检查。
- 当前组与目标不匹配时不再临时登记为 own 后删除；真正已有的外部连接仍在首次预检查被拒绝，即使其组名碰巧与新邀请相同也不能因此获得所有权。上次尝试的清理仅允许它原先请求的准确组名，新邀请码不赋予删除当前组的权限；移除复用既有系统断开确认及跨 manager 释放屏障。
- 地址等待的超时、取消均清除定时器，迟到 SDK 返回不能回填 owner 或重建轮询。成员尝试 generation 另封住 `CONNECTED` 完成到地址等待安装之间的取消缝隙，取消作为终止原因，不再重新发现或让旧候选取消更新的尝试。

验证：新增的 `p2p-join-readiness.cjs` 完整 `connectToLeader` 首入用例在修复前确定复现用户原文错误；修复后队长同意且 IP 延迟约 500ms 就绪能成功，只提交一次连接，不取消或删除正常连接。另覆盖 4 秒地址缺失保留原错误及已核实组的 abort 清理、同名或不同名已有外部连接均不提交请求/取消/移除、连接后组名不匹配不冒领、组查询硬超时后迟到结果不复活、地址等待中退出，以及 `CONNECTED` 后立即取消/组查询在途取消均不触发外层重新发现。旧 P2P 事件、漏事件轮询、拒绝/超时和迟到查询回归保留；`p2p-rejoin-lifecycle.cjs`、`member-join-session-reset.cjs`、`member-join-critical-path.cjs` 均通过。

最终 ArkTS 编译与 signed HAP 构建成功（5.309 秒），包为 `entry/build/default/outputs/default/entry-default-signed.hap`，未安装到设备；修改代码、新增测试及本文空白检查通过。本轮没有真机复测结果。应重点复测首次加入、队长同意后进入大厅、退出立即重加；若仍失败，保留完整 `[JoinDiag]`，尤其 `p2p-connected`、`p2p-group` 与 `p2p-release` 阶段，确认实际停在连接、组地址就绪还是释放步骤。
