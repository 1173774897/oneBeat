# 独立 MIC / LIVE 采集实验

## 进入与测试

退出队伍和单人练习后，在首页右下角长按 **SAME BEAT! 800ms**。这是隐藏实验入口，首页布局不变。实验不允许当前/尚未释放的 `AppSession` 或正式录制/保存并行运行。

- 支持 API 20+ 且系统声明 LIVE AEC 可用时，可启动普通 MIC / LIVE 对比。
- 同一个独立 `MetronomeEngine` 以 120 BPM 连续播放，只启动一次；普通 MIC 10 秒 → 释放后观察 2 秒 → LIVE 10 秒 → 释放后观察 2 秒。包括建立基准，约 28 秒。
- 不支持 LIVE 时仍可单独采集普通 MIC，约 14 秒，不偷偷改用语音通信类型。
- 每段前 5 秒安静观察节拍漏入，后 5 秒说话/拍手，保持手机位置、系统音量与输出设备一致。普通 MIC 可能本来就带系统处理，不能称为完全未处理的对照。
- 实验结束且采集/播放都释放后，可分别试听原始 MIC WAV，不叠加节奏、不归一化、不自动调增益。重测覆盖上一轮；清除按钮删除本实验文件。
- 离页、退后台、手动停止、系统中断、输入/输出路由变化均结束本轮，不在回前台时自动重启。返回等待资源清理完成。

## 隔离边界

### 当前验收口径（用户确认）

MIC 相对伴奏/视频的提前或延迟继续由用户手动调整，不以自动三路对齐作为本轮接入前提。主要验收条件是：MIC 的开启、运行、停止及异常恢复，不改变原伴奏的组队播放时间线、耳机校准和实际输出时延；手动 MIC 偏移仅作用于作品中的 MIC 轨，不能移动伴奏或共享节奏起点。

输入采集时间戳的拟合抖动与组队伴奏输出同步分别评估。当前单机扬声器实验未发现输出变化，但实验刻意不与正式 `AppSession` 共存，尚未证明真实双机组队/不同耳机条件下均无影响。后续应以真实组队 MIC 开停前后的伴奏相对拍点是否变化作为验收，不能用 MIC 时钟拟合结果代替。

正式 AVScreenCapture、混音器、录制状态机和共享节奏时钟保持原样。新采集只在单独页面使用 `AudioCapturer`，不接入正式录制。实验不会写耳机/输出/输入校准，不注册 `AudioOutputMonitor` 的全局单一监听，不切换系统音频场景或强选设备。

页面拥有独立 GAME renderer，输出补偿显式为 0。不能从大厅借用原 engine：即使大厅暂停，全局路由监听仍可能在 LIVE 启动后改动正式播放状态。页面进入及运行中持续检查 `AppSession` 不存在。

`MetronomeEngine` 仅增加只读诊断接口和焦点事件计数。诊断接口不 prime/rebase 生产帧映射；原焦点恢复策略及调度算法不变。原始硬件帧观察不要求生产帧原点精确，但也不会把原点改为精确；现有校准调用仍维持原门控。已有播放 PCM 基线和新增观察专项共同验证该边界。

`AppSession.hasLiveOrRetiringSession()` 是只读隔离判断：`reset()` 清空当前实例后，旧 renderer 与全局路由观察器可能仍在释放；实验同时检查 retiring session 和 reset promise，不只检查 `get()`。

## 观测与文件

应用私有 `filesDir/mic-capture-experiment/`：

| 文件 | 内容 |
| --- | --- |
| `mic.wav` / `live.wav` | 最新成功的原始 PCM16 WAV；48kHz，优先单声道，设备不支持时尝试立体声并报告真实格式 |
| `mic.json` / `live.json` | 对应真实格式、输入类型/角色、系统 AEC 声明、帧数、削波、溢出、硬件时间戳锚点、回调分批与输出观察 |
| `summary.json` | 本轮模式、结果/终止原因、系统能力、各阶段播放快照及两段结果；通过 `onStage` 即时接收的解绑/stop/release/分析/编码/写盘/rename 耗时在失败时也保留 |

不记录设备名称、MAC、帐号；不上传、不加入作品库或图库。回调仅拷贝到有界内存并统计；停止/释放后才写 WAV/JSON。捕获过程中不写文件、不插裁样本、不重采样、不用回调送达时刻冒充采样时刻。磁盘写入、取消与新 run 互斥。

每 100ms 读取硬件采集 frame/timestamp 和只读输出快照。完整 route/scene/latency 查询仅在基准、捕获开始前、native start 后首次观察、释放后及恢复观察结束等边界执行，避免频繁阻塞查询。输出设备事件单独订阅并以原 callback 单独退订。

停止条件包括 renderer/stream/物理起点改变、焦点事件、可查欠载计数改变、写入超过 800ms 不推进、路由/场景改变、硬件输出 frame/timestamp 粗跳变；双段实际输入不同也判为无效对比。输出时间戳容许约 20ms 帧量化，40ms 阈值只用于粗跳变保护，不是同步精度标准。

采集时钟分析使用硬件 frame ↔ timestamp 拟合，回调批处理偏差单列，不能解释为 MIC 延迟。短时钟稳定、AEC 能力声明、漏声较小都不能单独证明画音或双机同步。成功提示为“未发现可观测输出变化；仍需双机/耳机实测”。

## 接入正式录制前仍需验证

1. 扬声器、小音量/大音量、安静/说话/拍手条件下对比漏入节拍、人声损伤、削波和处理后拖尾。
2. 有线、USB、蓝牙耳机分别观察实际输入设备、是否切 HFP、输出路由/场景、延迟变化，以及启动与释放恢复行为。
3. 双机共同时间线与实际声学节拍并行验证，比较 MIC 开启前、运行中、停止后的两机伴奏相对拍点。MIC 起点允许用户手动提前/延后；禁止通过重置原节奏起点、修改耳机校准或平移伴奏来“对齐”录音。
4. 验证不支持 API/AEC 的设备，权限拒绝、后台、焦点打断、拔插设备、快速取消、存储异常及资源释放失败。
5. 本实验没有屏幕视频和内录合成，不能据此认定 AVScreenCapture + 独立 MIC 已自动三路对齐；自动对齐不再作为本轮前提，但需验证手动 MIC 偏移只影响成品 MIC 轨。正式接入应另设开关，并继续保留旧链路。

## UI 调整点

`entry/src/main/ets/pages/MicCaptureExperimentPage.ets`：

- `LAB_PAGE_INSET = 20`：加大两侧留白，卡片变窄；减小则变宽。内部卡片 `LAB_CARD_INSET = 16` 会进一步压缩可用内容宽度。
- `LAB_CARD_GAP = 16`：加大卡片间距，后续内容向下；减小则更紧凑。
- `LAB_BUTTON_HEIGHT = 46`：加大操作按钮高度，后续内容向下；减小则向上。结果卡试听按钮独立为 36。
- `LAB_LEVEL_HEIGHT = 12`：加大 MIC 电平条所在控件高度。进度条实际轨道由系统组件绘制。
- 页头 `padding.top = topSafeInset + 8`，正文 `padding.top = 8`：增加分别下移页头/正文；安全区仍以设备提供值为下限。

首页仅给现有 SAME BEAT 文案增加 LongPressGesture，`duration = 800` 控制触发毫秒数，无位置/大小修改，无新增图片素材。

## 验证记录

已连接的 API 26 真机声明 LIVE 支持 AEC，普通 MIC 未声明支持。首轮普通 MIC 原始48k单声道10000ms采集完整，无overflow，活跃期输出欠载计数始终为0；结束后欠载计数增加。第二轮阶段计时定位为“运行中解除readData监听”同步阻塞1000ms，随后native stop20ms、release15ms，实验按保护停止，未掩盖为成功。

因此实验模块停止顺序改为先禁止写入、停止native capturer，再解除监听并release。晚到回调不再进入PCM缓冲。

首次普通MIC有101个原始硬件锚点，其中2个连续零帧/零送达为初始化占位。仅在分析中排除该连续前缀（原始锚点保留），剩余跨度9844ms、P95残差4.214ms/最大5.902ms，仍严格标为`unstable`，没有放宽门槛。双机声学及耳机延迟尚不能据此判断。

最终修复版两段均完成10000ms/480000帧、48kHz单声道，输入同为内置MIC类型15/角色1。普通MIC stop17ms/off2ms/release13ms；LIVE stop28ms/off3ms/release50ms。分析24/34ms，WAV打包2–3ms，均未触发输出保护。

九个输出阶段保持同一stream、物理start计数1、焦点事件0、欠载0、扬声器路由2:1、scene0，报告延迟45ms（硬件40ms/软件5ms）。这些是系统可观测量，并非实测声学延迟。普通MIC时间戳P95 3.85ms，LIVE P95 7.54ms，两者均标为`unstable`；这限制根据硬件时间戳自动对齐的判断，不表示组队伴奏已失步，也不再作为用户接受手动 MIC 对齐时的接入门槛。回声残留/人声损伤仍需同条件人工试听，峰值降低不等于AEC效果已证明。真实双机组队及耳机共存测试仍待完成。

完整结果摘要见 [真机结果 JSON](mic-capture-experiment-device-results-2026-10-20.json)，不包含原音频及应用私有路径。真机另验证了退后台取消且回前台不自动恢复。`assembleHap`成功，最终同步回归门禁35/35全部通过，包括7项新增实验专项及既有节奏PCM基线；既有分享存储mock更新到当前服务已经使用的ImageKit/MediaKit/图库URI合同，没有修改分享产品逻辑。
