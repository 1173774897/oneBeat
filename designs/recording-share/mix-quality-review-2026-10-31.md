# 录制混音音质复盘与修复（2026-10-31）

目标：行进页录制产出高品质作品。MIC 主要收**乐器**，不是人声。

## 本次改动

### 1. 耳机输出不再使用 LIVE AEC

- `RecordingCoordinator.startExclusive`：`systemAecMic = !headphoneCapture && supportsSystemAecMic()`。
- 依据：LIVE 的 AEC/NS 面向语音，会损伤乐器音色和瞬态；耳机输出时伴奏不会经空气进入 MIC，没有回声可消。
- 判定：`AudioOutputMonitor.isHeadphoneOutputActive()`，节拍 GAME renderer 的首选输出**全部**为有线耳机、USB 耳机、A2DP、SCO 或星闪时才为 true；查询失败返回 false（保守地走 AEC）。A2DP 无法区分蓝牙音箱和耳机，按耳机处理。
- 耳机录制走原录屏 MIC（mapping 2，`builtInSpeakerCapture=false`，不做 FIR）。录制中切换路由本来就会结束录制，所以开始时的选择全程有效。
- 外放仍用 LIVE AEC：这是去回声和乐器保真之间的取舍。

### 2. 最终混音由硬截断改为前瞻峰值限幅

- `recording_audio_math.h` 的 `LookaheadPeakLimiter`：5ms 窗口内取最小值再做同长度箱式平均，60ms 释放，延迟 239 帧（导出时先预读，再补齐）。
- 约定：混音和不超出 S16 范围时增益**精确等于 1**，逐样本与旧实现一致（含 MIC=0 时伴奏逐位不变）；超出时平滑压低，永不越界，也不做波形整形。
- 上限仍为 S16 满幅，没有改成 -1 dBTP，因为那会改变不削波作品和 MIC=0 的输出。是否改，等日志里的 `busPeak` 数据再决定。
- 混音版本号**未提升**：旧作品只有在用户调整音量或对齐、重新导出时才会经过限幅器。如果日志证明削波常见，再提升 `RECORDING_MIX_VERSION` / `SYSTEM_AEC_MIX_VERSION`，让旧作品统一重新合成。

### 2b. 鼓机总线限幅（2026-11-01，影响现场播放和录制）

- 问题：鼓声素材都归一化到约 -0.7 dBFS，`MetronomeEngine` 渲染小节时每叠加一个鼓件就硬截断一次。用真实素材离线叠加（120 BPM，4/4，3 种节奏型含加花），12 种内置风格里 11 种几乎每小节都削波，最大峰值：disco +6.6 dBFS（重拍 ×1.15 时 +7.8），techno / house 约 +5.3，rock / trap / hiphop / jazz / dnb 约 +2.3 ~ +2.9，latin +0.6。**现场播放的声音本身就是削过波的**，录制只是原样录下来，录制端的限幅救不回来。
- 修复：`mixBar` 叠加时不再截断（每层仍按原方式取整），`renderSequence` / `renderBar` 最后统一交给 `audio/DrumBusLimiter.ets` 的 `limitDrumBus`。
- 约定：在准备 PCM 时离线处理，不在 writeData 中运行；**零延迟**，每个样本仍在原来的帧位置，小节长度、拍点和组队时间轴不变；不越界时逐样本与旧实现一致（回放基线 54 条路径通过）；越界时提前 5ms 平滑压低、60ms 释放，永不越界、不反相；循环序列的末尾会为回到开头的重拍提前压低。
- 日志：越界时打印 `[DrumBusDiag] bars overSamples limitedSamples peakDbfs minGainDb`（每次准备序列时打印一次）。
- 后果：鼓机伴奏峰值会贴近满幅，录制时和 MIC 叠加更容易越界，由录制端的限幅器处理。如果试听觉得鼓机整体压得太狠（例如 disco 底鼓变软），下一步再考虑给鼓机总线留固定余量。

### 2c. 上限、鼓机余量与 MIC 范围（2026-11-01 第三版）

依据 A2 / G 的真机数据（见下文"真机结果"），用户确认：
- **两个上限都降到 -1 dBFS**：录制混音（`LookaheadPeakLimiter::CEILING = 29204`）和鼓机总线（`DRUM_BUS_CEILING = 29204`）。原因：0 dBFS 上限的作品经 AAC 编码后真峰值达到 +0.2 dBTP。代价：峰值在 -1 ~ 0 dBFS 之间的作品会被压低最多 1 dB；"MIC=0 时伴奏逐位不变"只在伴奏峰值不超过 -1 dBFS 时成立。
- **鼓机素材固定 -3 dB**：`MetronomeEngine` 的 `DRUM_KIT_GAIN`，只作用于音色包里的鼓件，`accent` / `weak` 节拍器咔哒音保持原音量。现场播放的鼓机会变小声约 3 dB，时间轴不变。即使这样，12 种风格 × 普通 / 重拍共 24 种情况里仍有 19 种需要限幅（disco 约压低 4.6 dB）。
- **MIC 滑杆 0–400%**：`RecordingMixer.MAX_MIC_GAIN = 4`，原生 `MixFile` 的检查同步改为 4。界面位置在 `RecordingLibraryPage.ets` 的 MIC `Slider`（`max: MAX_MIC_GAIN`），右侧刻度文字跟随常量显示 400%，位置和尺寸不变。
- 测试：鼓机测试里"检查位置和音色"的用例把实例字段 `drumKitGain` 设为 1，以保持原来的标记值；`metronome-drum-preview-seek.cjs` 断言正式默认值确实是 -3 dB。

## 真机验证清单（2026-11-01 第二版，需安装 11-01 08:03 之后的包）

### 规则

- MIC 模式在**开始录制时**按输出设备确定，录制中切换输出设备会直接结束录制。所以外放和每种耳机必须分开录。
- 日志里的峰值和跳变都是**整段**统计，需要对比的条件必须分成不同条录制。
- MIC 增益是录完后在作品页调整的。每次导出（保存一次，之后每次调增益或对齐各一次）都会打一条 `[RecordingMixDiag]`；调整时 `cacheBuilt=0` 属于正常情况。
- 鼓机日志 `[DrumBusDiag]` 在选择或修改鼓机节奏、开始播放时打印，不需要录制。

### 检查项与判读

1. **削波**：看 `busPeak` / `overFrames`。`busPeak>0` 说明旧实现会削波，`limitedFrames`、`minLimiterGainDb` 显示限幅器压了多少。
2. **内录电平**：已有结论，和系统音量无关。
3. **暂停断档**：看 `innerMaxStep`、`innerMaxStepAt`。约 240000 帧（5 秒）说明暂停那段被挤掉了，之后伴奏整体提前；接近 0 说明暂停期间系统仍在回调，没有问题。修复时只在大于约 50ms 的断档处补静音，不回到按抖动插零。
4. **AAC 预填充**：看 `aacPackets×1024 − aacInputFrames` 和 `aacFirstPtsUs`。成品 MP4 可以用 `hdc file recv -b com.onebeat.app /data/storage/el2/base/haps/entry/files/recordings/<id>.mp4` 取出分析。
5. **耳机**：应出现 `mode=screen-mic headphone=true`，输出四个阶段不变、没有切到通话链路。有线、USB 耳机暂无设备，待验证。
6. **AEC 软拐点**：Pura X 外放已确认 MIC 峰值被卡在 -9.12 dBFS（0.35 FS），受影响样本 0.12–0.17%。是否替换为交给总线限幅器处理，等鼓机和 200% 的结果出来一起决定。
7. **鼓机**：降 3 dB 后，`[DrumBusDiag]` 的 `peakDbfs` 应比 G 低约 3 dB（rock 约 +0.7、disco 约 +2.6），`minGainDb` 相应变浅；作品 `innerPeak` 应约为 -1.0 dBFS，`innerRms` 比 G 低约 3 dB。主观试听：和更新前相比，底鼓和军鼓是否不再"破"，整体是否压得太软。
8. **MIC 跳变**：看 `micMaxStep`、`micMaxStepAt`、`micGaps`、`micFirstGapAt`（只有录屏 MIC 有意义）。跳变在开头（`MaxStepAt` 接近 0）说明是启动时的批量回调，无害；在中途、约 3840 帧说明丢了约 80ms 数据，需要修复。

读日志：`hdc hilog | grep -E "RecordingMixDiag|RecordingTimeline|RecordingMic|RecordingOutputDiag|DrumBusDiag"`

### 外放往返延迟（MIC 采集实验页，2026-11-01）

方法：实验页用 120 BPM 咔哒声外放。把 MIC 的硬件帧时间戳线性拟合后换算到应用时钟，换算差值取引擎日志 `[ClockDiag] clockOffset`（与播放端换算用的是同一个差值，误差会抵消）；再把 MIC 高通能量包络按 500ms 节拍相位叠加平均，峰值处的延迟就是"引擎计划的发声时刻 → 被 MIC 录到"的往返延迟。脚本：`micexp/fold.py`、`latency.py`（放在会话临时目录，没有进仓库）。

| 机型 | 普通 MIC | LIVE AEC |
|---|---|---|
| Pura X（VDE-AL10） | 109ms（单下咔哒声 108.8–109.0ms） | 133ms（AEC 残留，+29.5 dB） |
| Pura 80（LMR-AL00） | 122ms | 测不出（AEC 几乎完全消除了咔哒声） |

- 系统报告的外放输出延迟是 45ms（硬件 40 + 软件 5），实际往返延迟比它多约 65–75ms。
- LIVE 的处理延迟（Pura X 约 +24ms）没有反映在 MIC 硬件时间戳里。
- Pura 80 的 LIVE 往返延迟可以从 G2 rock 的残留推出：141ms，比普通 MIC 多约 19ms（Pura X 为 24ms）。
- 补偿原理：用户跟着扬声器实际放出的声音演奏，所以 MIC 提前一个往返延迟，演奏就正好对在拍子上；同时 AEC 残留会和原鼓点重合，不再是单独的回声。这个值恰好就是咔哒声的往返延迟。
- 更正：G2 第一次分析曾把这份残留误判为"用户拍手晚了"，用户确认没有拍手后撤回。教训：残留和演奏在包络上无法区分，必须以录制时的实际操作为准。
- 耳机（D）里用户拍手只晚 0–60ms，和"输出延迟 285ms"对不上，原因还没查明；耳机不会漏音给 MIC，无法用这个方法测。

还没有结论的项：
- D 的录屏 MIC 时间线：`micMaxStep=3840`（80ms），结束时 `micDriftLast=1960`（约 41ms）。可能是中途少交付了数据（之后的 MIC 会提前约 40ms），也可能是批量回调造成的时间戳抖动。需要再加一条日志，记录跳变发生的位置才能区分。伴奏时间线正常（最大跳变 59 帧）。

## 已踩过的坑（改录制/混音前先读）

- Surface 编码器输出的 PTS 是纳秒：直接当微秒写入，3 秒视频被写成 3075 秒。（README，10-18）
- 不能按回调时间戳抖动插零或裁样本：会产生周期性断缝。PCM 只能连续写入。（README）
- 不能把同一份内录扣到 MIC 的两个声道上：左右声道拾音差别很大，右声道会出现反相节奏。必须逐声道拟合，并且少扣 2% 防止反相拖尾。（README，10-19）
- 录屏回调中除"应用声 / MIC"以外的音频类型不能混入（会出现重音、金属声）；PCM 不能按缓冲区属性里的 offset/size 截取。（`recording_native.cpp` 注释）
- 录屏接口不能指定 LIVE 音源，需要单独建采集器；不能退回 VOIP/通话模式，也不能改伴奏的 GAME 播放类型。（production-system-aec）
- 采集器运行中解除数据监听会同步卡住 1000ms：必须先停止，再解除监听，最后释放。（mic-capture-experiment）
- 采集硬件时间戳 P95 约 4–7.5ms，不稳定，不能靠它自动对齐。
- `MicLoopbackCalibrator` 测得的输入延迟不能直接拿来补偿录制，会重复补偿；也不能把用户的演奏自动拉到拍点上。（mic-echo-and-timing-assessment）
- 修改 MIC 缓存的算法时，必须同时提升缓存版本和混音版本，旧作品会从原始音轨重新合成一次。
- `8f66535`（提交说明为 "shadow method"）里混入了 AEC 电平修改：99.95 百分位峰值加 tanh 软拐点，缓存升到 `system-aec-v3`、混音版本 8，当时没有写文档。

## MIC 中的鼓声残留：开源方案对比与最小验证（2026-11-01）

### 现状
- 外放 + 系统 LIVE AEC：Pura 80 rock 的高频残留比鼓声低 27.6 dB（MIC 100%）、15.5 dB（400%），延迟 141ms。用户手动提前 130ms 后，残留和鼓机底鼓重合，听不出回声。默认提前**暂不做**，由用户手动调整。
- 需求特点：输入**已经过系统 AEC**，剩下的是非线性残留；可以**离线**处理，并且有**精确完整的参考信号**（伴奏原轨）和已知延迟；**48kHz 立体声音乐**，近端是乐器而不是人声。

### 参考项目

| 项目 | 解决的场景 | 依赖 | 和当前需求的差异 | 可借鉴 |
|---|---|---|---|---|
| WebRTC AEC3（独立打包版：PulseAudio 的 webrtc-audio-processing） | 实时语音通话的全双工回声消除：线性自适应滤波 + 残留回声估计 + 抑制增益 + 舒适噪声 | C++17、abseil-cpp、meson 构建；以 10ms 帧实时流式处理 | 为语音调参，抑制很激进，会压掉乐器；在系统 AEC 之后再跑一遍等于重复处理；需要实时延迟估计（我们已经知道精确延迟） | 线性滤波不可用时，退回到用参考信号功率估计残留，并减去稳态噪声以免过度抑制 |
| SpeexDSP（MDF 回声消除 + preprocess 残留回声抑制） | 语音通话：频域分块自适应滤波（MDF）+ 预处理器里的残留回声抑制 | 纯 C，无第三方依赖 | 同样是语音取向；它的线性部分在我们这里没有可消的东西（见下面第 1 档）；残留抑制默认很深 | 残留抑制和线性回声消除共享回声状态的结构 |
| DTLN-aec | 深度学习语音回声消除（微软 AEC Challenge 第 3 名），近端 MIC + 远端参考 | TensorFlow Lite 运行时和模型（1.8M–10.4M 参数），16kHz | **16kHz**：会丢掉 8–24kHz；用语音训练，会把乐器当回声或噪声处理掉；需要额外的推理运行时 | 不适用 |
| NKF-AEC | 低复杂度神经卡尔曼滤波回声消除（ICASSP 2023），模型只有 5.3K 参数 | PyTorch 推理，16kHz；README 说明是**线性**回声消除器，延迟大时要先对齐 | 16kHz；只做线性消除，而我们的残留不是线性的 | 不适用 |

### 最小验证（离线原型，在会话临时目录，不进仓库；无第三方依赖）

在 Pura 80 G2 rock 的 MIC 缓存上，用伴奏原轨作参考；STFT 2048 点、帧移 512，每个频点建模 0–256ms 的延迟。近端损伤的测法：把 Pura X D 那条（耳机、无鼓声泄漏）的干净 MIC 按同等电平叠加进去，处理后比较。

| 方案 | 高频残留（400%） | 近端电平 | 近端 SDR |
|---|---|---|---|
| 不处理 | -15.5 dB | — | — |
| 第 1 档：频域线性消除（类似 MDF / AEC3 线性部分） | -15.7 dB（几乎无效） | — | — |
| 第 2 档：线性消除 + 残留抑制 | -16.8 dB | — | — |
| 第 3 档：功率域残留抑制，轻（α=1，下限 -15 dB） | -18.7 dB | -0.19 dB | 20.0 dB |
| 第 3 档：中（α=2，下限 -20 dB） | -20.9 dB | -0.29 dB | 17.1 dB |
| 第 3 档：重（α=4，下限 -30 dB） | -23.7 dB | -0.43 dB | 14.4 dB |

- 线性方法几乎无效，证实残留是非线性的（扬声器大音量失真，加上系统 AEC 随时间变化的残留）。
- 功率域抑制能降低 3–8 dB，代价是近端保真度下降，二者此消彼长。
- 性能：未优化原型在 Mac 上处理 27 秒立体声约 3.5 秒，手机上估计会慢 2–4 倍。
- 试听文件（rock，MIC 400%）：`listen/rock400_1-原样_对齐0`、`2-中等抑制_对齐0`、`3-原样_提前130ms`、`4-中等抑制_提前130ms`，都放在会话临时目录。

## 外放 AEC 自动对齐：单条测量 + 按手机记住（2026-11-01；"按手机记住"已于 2026-11-02 去掉，见第三版）

用户确认：对齐后残留和鼓机原声重合，"至少不乱"；不希望用户手动操作，所以由导出流程自动探测残留和原声之间的偏差。

### 做法
- `entry/src/main/cpp/recording_residual_lag.h` 的 `ResidualLagEstimator`：在第一次生成 MIC 缓存时，取伴奏原轨和原始 MIC（level 补偿之前）的 1kHz 以上包络（2ms 一格），做非负反卷积 `micEnv(t) ≈ Σ h[L]·innerEnv(t−L) + c`（L = 0–300ms），再在 60–250ms 内找冲激响应能量最集中的 10ms 区间。用伴奏包络的自相关构造矩阵（Toeplitz 近似），计算量随时长线性增长：80 秒录音约 70ms。
- 判定可靠的条件：该区间能量占比 ≥ 0.2，且重叠时长 ≥ 10 秒。真机数据：rock 0.28（134ms，和用户手动对齐的 130ms 吻合；只取前半段为 0.44、130ms）；disco 0.11、Pura X B 0.00、A2 0.09，都判为不可靠。
- 可靠时：自动基准 = −延迟（MIC 提前），置信度为占比。
- 不可靠时：如果这台手机记住过外放 AEC 的往返延迟，就用记住的值，此时置信度记为 0，表示"来自记忆，不能再拿来学习"；没有记忆则不调整。
- 记忆：`RecordingRoundTripMemory`，保存在 `recordings/acoustic-round-trip-v1.json`，只接受 60–250ms 的值，只从单条录音自己测得的可靠结果更新。删除应用后记忆随之清除。
- 只作用于"系统 AEC + 外放"（`builtInSpeakerCapture === true`）。耳机走录屏 MIC，没有残留可测，保持手动；今天以前录的"AEC + 耳机"旧作品也不测、不套用记忆。
- 版本：AEC 缓存升到 `system-aec-v4`，`SYSTEM_AEC_MIX_VERSION` 升到 9，旧 AEC 作品打开时会重新测量一次；删除作品时一并清理 v1–v3 缓存。自动偏移上限：旧的 FIR 路径仍在 30ms 以内；外放 AEC 放宽到 250ms，加上手动 ±300ms，有效上限为 550ms。
- 日志：`[RecordingMixDiag] ... residualLagUs residualShare autoShiftUs autoReliable remembered`。
- 作品页已有的"已自动提前 X 毫秒，可继续微调"提示保持不变，用户仍可以在此基础上手动微调。

### 为什么不用回声消除之前的 MIC 测延迟
- LIVE 源只把回声消除之后的结果交给应用；同时再开一路普通 MIC 会重复采集，还可能改变音频焦点和路由，代码里特意禁止过。
- 即使拿到了也不准：Pura X 普通 MIC 往返 109ms，LIVE 为 133ms，AEC 本身增加约 24ms。进入成品的是 LIVE 的输出，所以需要的正是"LIVE 残留相对伴奏"的延迟。
- 系统 AEC 在系统内部完成，"先测延迟再消除"的顺序改不了；如果改为录原始 MIC 再离线自己做回声消除，线性方法对非线性残留无效（见上一节）。

### 测试
- `scripts/tests/recording-residual-lag.cpp`：在 250ms 周期的鼓点下，109 / 133 / 141 / 200ms 的残留都能准确测出（误差 ≤ 4ms）；只有噪声、残留远低于底噪、短于 10 秒时都判为不可靠。
- `scripts/tests/production-system-aec-mix.cjs`：使用真实的记忆模块（文件读写换成内存版），覆盖：第一次测到后会记住并写入文件；已测量的作品在后续调整中保留自己的基准；测不准时使用记忆，且不会反过来改写记忆；耳机 AEC 不测量也不套用记忆；新手机没有记忆时不调整；不合理的值和损坏的文件都会被忽略。
- 完整回归 75/75 通过，`assembleHap` 成功。

### 第一次真机试用后的修正（2026-11-01 第二版，混音版本 10，缓存 `system-aec-v5`，记忆 `acoustic-round-trip-v2.json`）

用户反馈：旧 disco 作品先被打开，没能用上 rock 的测量结果；rock 自动对齐后反而错开，把滑杆拨回中间（显示"已自动提前 134 毫秒"）才对齐。

日志定位到两个问题：
1. **旧作品的手动偏移被叠加到新的自动偏移上**。旧的手动值是在"自动 = 0"的前提下调的，升级后自动变成 -134ms，手动值原样保留，导致重复补偿。
2. **Pura X disco 的假阳性**：测得 158ms，比例 1.00，但 R² 只有 0.0001，冲激响应几乎全为 0。Pura X 的 rock 测不准，又套用了这个错误记忆。

修正：
- 可靠条件增加强度门槛：`explained`（伴奏模型能解释的 MIC 包络方差比例）≥ 0.01。真机：Pura 80 rock 0.039（可靠）；Pura X disco 0.0001、rock 0.003、B 0.004（都不可靠）。
- **升级不改变已调作品的听感**：混音版本升级时一律重新测量。手动值不为 0 的作品，原生按"新手动 = 旧手动 + 旧自动 − 新自动"反推（取整到毫秒，限制在 ±300ms 内），实际偏移保持不变；手动值为 0 的作品直接采用新测量。作品页在合成完成后同步滑杆，避免用旧值再合成一次把它覆盖。
- **补上记忆**：没调过手动、自己又测不准（或之前已采用过记忆）的外放 AEC 作品，在手机记忆出现或更新后，`RecordingMixer.isRenderCurrent()` 会返回 false，下次打开时直接复用缓存、改用记忆值（置信度记为 0，不会反过来改写记忆）。这解决了打开顺序带来的问题。调过手动的作品、自己测量可靠的作品、耳机作品都不受记忆影响。
- 记忆文件升到 v2，旧的 v1（可能含假阳性）一律不用。

本次升级对现有作品的影响（按当时保存的数据推算）：
- Pura 80 rock：手动 0，重新测得 134ms，自动提前 134ms，并写入记忆。
- Pura 80 disco：手动 0，测不准；如果打开时 rock 已经学到记忆，就采用 134ms，否则先为 0，等 rock 学到后再次打开时补上。
- Pura X rock：手动 +180、旧自动 -158（来自错误记忆），重新测量不可靠，自动变为 0，手动反推为 +22ms，实际偏移不变。
- Pura X disco：手动 -250、旧自动 -158，实际偏移 -408ms 超出手动范围，反推后被限制为 -300ms，听感会有变化；需要用户把它调回 0。

### 第三版：去掉"按手机记住"（2026-11-02，混音版本仍为 10，缓存仍为 `system-aec-v5`）

真机数据否定了"往返延迟是手机固定属性"这个前提，三条 Pura 80 外放 AEC 作品：

| 作品 | MIC 里跟着伴奏的主要内容 | 测得延迟 | 用户听感 |
|---|---|---|---|
| 旧单人 rock（740af8bd） | 回声残留（底鼓回音） | 134ms（share 0.28） | 提前约 130ms 后对齐 |
| 新单人 rock（5201de7d） | 演奏本身（130ms 附近已无残留，MIC 中位电平 -52 dBFS） | 62ms（share 0.35，explained 0.083） | 自动提前 62ms 后对齐 |
| 多人 10:27（cdae2612） | 演奏（信号弱，share 0.04） | 约 +30ms（起音点对比） | 不偏移就对齐 |

结论：
- 估计器测量的是"MIC 里跟着伴奏走的内容"晚了多少。残留听得见时测到的是残留，残留被消干净时测到的是演奏本身。两种情况下按单条结果提前，用户听感都对。
- 这个延迟取决于每条作品的内容，不是手机的固定属性。记忆恰好用在测不准的作品上，而这些作品往往残留很弱，真正要对齐的只有演奏，这时套用别的作品的值反而会错开（例如多人作品套用 62ms 会提前约 30ms）。
- 之前"按往返延迟提前，残留和演奏会一起对齐"的假设不成立，代码注释已一并更正。

修改：
- 删除 `RecordingRoundTripMemory.ets`，原生的 `fallbackAutoMicShiftUs/Known` 参数也一并删除。测不准的作品自动基准一律为 0。
- 应用启动时删除 `acoustic-round-trip-v1.json` 和 `-v2.json`。
- 已经套用过记忆的作品（可靠但置信度为 0，`RecordingMixer.hasDeviceMemoryBaseline()`），`isRenderCurrent()` 返回 false，下次打开时用自己的音轨重新测量。调过手动的作品按"新手动 = 旧手动 + 旧自动 − 新自动"保持实际偏移。安装时检查过两台手机，没有作品处在这种状态。
- 日志：`adopted`、`remembered` 字段去掉，`upgrading` 改为 `remeasure`。

已知限制：搜索区间仍是 60–250ms。演奏延迟低于 60ms 的作品（比如那条约 +30ms 的多人作品）测不到，自动基准保持 0；从这条作品的听感看，这样是可以接受的。
